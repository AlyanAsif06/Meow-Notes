What's a Semaphore? (Quick Recap)

Before we dive into today's problems, let's remember what a semaphore actually is.

Real-World Analogy — Traffic Light

Imagine a one-lane bridge. Only ONE car can cross at a time. A traffic light controls access: 🟢 green = enter, 🔴 red = wait. A semaphore is like that traffic light for processes sharing a resource in your OS.

A semaphore is a special integer variable. It has exactly two operations:

wait(S) — also called P(S)

Before entering the critical section.
If S > 0: subtract 1 and go in.
If S = 0: block and wait.

signal(S) — also called V(S)

After leaving the critical section.
Add 1 to S.
Wake up a waiting process (if any).

Semaphore Operations
// wait(S) — "I want to enter, please check if I can"
wait(S) {
    while (S <= 0)
        ; // busy wait / sleep — just keep checking
    S--;  // decrement: one fewer slot available
}

// signal(S) — "I'm done, someone else can come in now"
signal(S) {
    S++;  // increment: one more slot available
}
Section 2

⚠️ Problems With Semaphores

Semaphores are powerful, but they're also dangerous if used incorrectly. Here's the big issue:

The Core Problem

The wait() and signal() calls are scattered all over your code — across many different processes. If even ONE process uses them wrong, the entire system of cooperating processes can break!

Imagine 10 students sharing one printer. All 10 must follow the same rules for the printer semaphore. If one student writes bad code and forgets to call signal() when done — every other student's print job freezes forever. 💀

There are three main problems that come from incorrect semaphore use:

1. Deadlock

Two or more processes wait for each other forever. Nobody makes progress.

2. Starvation

A process waits forever because others keep getting priority. It never gets its turn.

3. Violation of Mutual Exclusion

Two processes enter the critical section at the same time — chaos!

The Solution (for later chapters)

These problems led computer scientists to invent higher-level constructs like critical regions and monitors — which hide the wait/signal complexity from the programmer.

Section 3

🔒 Deadlock

"A set of processes are in a deadlock state if every process is waiting for an event that can only be caused by another process in the same set."
Real-World Analogy — Traffic Jam

Picture 4 cars at a 4-way intersection. Car A won't move until Car B moves. Car B won't move until Car C moves. Car C won't move until Car D moves. Car D won't move until Car A moves. Nobody moves. Ever. That's a deadlock. 🚗🚗🚗🚗

The 4 Conditions for Deadlock

Deadlock can only happen when ALL four conditions exist at the same time:

1

Mutual Exclusion

A resource can only be used by one process at a time.

2

No Preemption

You can't forcibly take a resource away from a process holding it.

3

Hold and Wait

A process holds one resource while waiting to get another.

4

Circular Wait

P1 waits for P2, P2 waits for P3, P3 waits for P1 — a cycle!

Code That Causes Deadlock

deadlock_example.c
semaphore A = 1;  // controls Resource A
semaphore B = 1;  // controls Resource B

// --- Process P1 ---
wait(A);   // P1 grabs Resource A ✅
wait(B);   // P1 tries to grab B... but P2 has it! 😱 BLOCKED
// ... use both A and B ...
signal(B);
signal(A);

// --- Process P2 (runs at same time) ---
wait(B);   // P2 grabs Resource B ✅
wait(A);   // P2 tries to grab A... but P1 has it! 😱 BLOCKED
// ... use both A and B ...
signal(A);
signal(B);

// RESULT: P1 waits for B (held by P2).
//         P2 waits for A (held by P1).
//         DEADLOCK! Neither can continue. 💀
Section 4

😩 Starvation

Starvation is when a process never gets the resources it needs because other processes keep cutting in line.

Real-World Analogy — School Cafeteria

You're waiting to use the only computer in the library. Every 5 minutes, a new person shows up and jumps the queue. You've been waiting for 3 hours. You're not blocked — the computer is being used — but you never actually get a turn. That's starvation! 🍽️

Key Difference from Deadlock

Deadlock = everyone is frozen, no progress at all.
Starvation = the system keeps running, but ONE unlucky process never gets its turn.

Starvation usually happens when a scheduling policy is unfair — for example, always serving the "shortest job" first. A long process may never run if short processes keep arriving.

How to Fix It

Use an aging technique: the longer a process waits, the higher its priority grows. Eventually it becomes so high priority that it must be served next.

Section 5

🔢 Two Kinds of Semaphores

Binary Semaphore

Value is only 0 or 1.
Like a light switch: ON or OFF.
Used for simple mutual exclusion (mutex).

S = 0 or 1

Counting Semaphore

Value can be any non-negative integer.
Like counting available parking spots.
Used to control access to a resource with multiple instances.

S = 0, 1, 2, 3, ... N
Analogy — Parking Lot

A parking lot has 5 spaces. The semaphore starts at 5. Every car that enters does wait(S) (reduces count). When a car leaves it does signal(S) (increases count). When count = 0, the next car must wait outside. This is a counting semaphore! 🅿️

Section 6

🔧 Implementing a Counting Semaphore Using Binary Semaphores

What if your OS only gives you binary semaphores? You can build a counting semaphore from scratch using two binary semaphores + an integer variable!

Data Structures Needed

counting_semaphore_setup.c
binary_semaphore S1;  // controls access to the counter C
binary_semaphore S2;  // used for blocking processes that must wait
int C;               // the actual count (initial value of our semaphore)

// Initial values:
S1 = 1;  // S1 starts open (unlocked)
S2 = 0;  // S2 starts locked — processes will block here if C <= 0
C  = N;  // N = initial value of our counting semaphore (e.g., 3)

wait(S) — Implemented with Binary Semaphores

wait_implementation.c
void wait() {
    wait(S1);        // 🔒 Lock S1 so only we can touch C right now
    C--;             // Decrease the count (we're trying to use a resource)
    
    if (C < 0) {
        // Count went negative — no resource available, we must block
        signal(S1);    // 🔓 Unlock S1 first (be polite, let others update C)
        wait(S2);      // 😴 Now block ourselves on S2 until someone wakes us
    } else {
        // Count >= 0, resource available! We can proceed.
        signal(S1);    // 🔓 Unlock S1
    }
    // Now we're inside the critical section!
}

signal(S) — Implemented with Binary Semaphores

signal_implementation.c
void signal() {
    wait(S1);        // 🔒 Lock S1 — we need exclusive access to C
    C++;             // Release: one more resource available
    
    if (C <= 0) {
        // C was negative, meaning someone is blocked waiting on S2
        // Wake them up!
        signal(S2);    // 🔔 Wake up one sleeping process
    }
    
    signal(S1);      // 🔓 Unlock S1
}

Properties of This Counting Semaphore

PropertyResultWhy?
Mutual ExclusionNoMultiple processes can be in the critical section simultaneously (up to N)
ProgressYesIf a process is waiting and a spot opens, it will eventually get in
Bounded WaitingYesA process won't wait forever; there's a bound on how long it queues
Remember This!

The value of C ranges from 0 to N, where N is the number of processes/threads that can simultaneously be in the critical section. This is what makes it "counting."

Classic Problem 1

📦 The Bounded-Buffer Problem

Analogy — McDonald's Kitchen

There's a counter (buffer) with N slots. The cook (producer) makes burgers and puts them on the counter. The cashier (consumer) takes burgers from the counter to give to customers. Problems: the cook can't put a burger down if the counter is full. The cashier can't take a burger if the counter is empty.

Shared Data (Semaphores Used)

bounded_buffer_shared.c
semaphore mutex = 1;  // Mutual exclusion: only 1 process touches buffer at a time
semaphore full  = 0;  // Counts FULL slots  (starts at 0 — nothing in buffer)
semaphore empty = N;  // Counts EMPTY slots (starts at N — buffer all empty)

// Think of it like this:
// full  = "how many items can the consumer take?"
// empty = "how many items can the producer add?"
// mutex = "is anyone touching the buffer right now?"

Producer Code

producer.c
do {
    // Step 1: produce an item
    item = produce_item();

    // Step 2: wait for an empty slot
    wait(empty);
    // (if empty == 0, block here)

    // Step 3: get exclusive access
    wait(mutex);

    // Step 4: add item to buffer
    add_to_buffer(item);

    // Step 5: release lock + signal
    signal(mutex);  // unlock
    signal(full);   // one more full slot!

} while (true);

Consumer Code

consumer.c
do {
    // Step 1: wait for a full slot
    wait(full);
    // (if full == 0, block here)

    // Step 2: get exclusive access
    wait(mutex);

    // Step 3: remove item from buffer
    item = remove_from_buffer();

    // Step 4: release lock + signal
    signal(mutex);  // unlock
    signal(empty);  // one more empty slot!

    // Step 5: consume the item
    consume_item(item);

} while (true);

Classic Problem 2

📖 The Readers-Writers Problem

Analogy — Library Book

Many students can read the same book at the same time — no problem! But if someone wants to write notes into the book, they need exclusive access — nobody else can read OR write while they do it.

The Rules

Readers (READ only)

Multiple readers can access the data simultaneously — reading doesn't change anything, so there's no conflict.

Writers (READ + WRITE)

Writers need EXCLUSIVE access. No readers or other writers allowed while a writer is working.

The Two Variations

1

First Readers-Writers Problem (Readers get priority)

No reader waits unless a writer already has access. If readers keep arriving, a writer might starve.

2

Second Readers-Writers Problem (Writers get priority)

Once a writer is ready, it writes ASAP. New readers can't start if a writer is waiting. Now readers might starve.

Both Variants Can Starve!

In the 1st case, writers may starve. In the 2nd case, readers may starve. There's no perfect solution — it's a classic trade-off.

Solution: First Readers-Writers Problem

readers_writers_shared.c
semaphore mutex   = 1;  // protects readcount variable
semaphore wrt     = 1;  // controls access to the shared object (for writers)
int       readcount = 0; // how many readers are currently reading

Writer Process

writer.c
do {
    // Wait until no readers/writers
    wait(wrt);

    // ✍️ Write to the shared object
    write_data();

    // Signal: done writing
    signal(wrt);

} while (true);

Reader Process

reader.c
do {
    wait(mutex);       // lock readcount
    readcount++;
    if (readcount == 1)
        wait(wrt);     // 1st reader blocks writers
    signal(mutex);     // unlock readcount

    // 📖 Read the shared object
    read_data();

    wait(mutex);       // lock readcount again
    readcount--;
    if (readcount == 0)
        signal(wrt);   // last reader unblocks writers
    signal(mutex);     // unlock readcount
} while (true);
Why is readcount important?

The first reader to arrive locks out writers (wait(wrt)). The last reader to leave unlocks writers (signal(wrt)). This allows many readers to coexist while keeping writers safe.

Classic Problem 3

🍜 The Dining Philosophers Problem

This is the most famous synchronization problem in all of Computer Science!

The Setup

5 philosophers sit around a circular table. They alternate between thinking and eating.

There are exactly 5 chopsticks, one between each pair of adjacent philosophers.

To eat, a philosopher needs both the chopstick on their left AND the chopstick on their right.

The Challenge

Chopsticks are shared! Philosopher 1's right chopstick is Philosopher 2's left chopstick. How do we prevent deadlock and starvation?

The Basic Solution (and Why It Can Deadlock!)

dining_basic.c — NAIVE SOLUTION (HAS DEADLOCK!)
// Each chopstick is a semaphore, initialized to 1 (available)
semaphore chopstick[5];
// All 5 initialized to 1

// Philosopher i's structure:
do {
    // Think for a while...
    think();

    // Try to pick up LEFT chopstick
    wait(chopstick[i]);           // chopstick[i] is to the LEFT

    // Try to pick up RIGHT chopstick
    wait(chopstick[(i+1) % 5]);   // (i+1)%5 is to the RIGHT

    // 🍜 EAT!
    eat();

    // Put down both chopsticks
    signal(chopstick[i]);
    signal(chopstick[(i+1) % 5]);

} while (true);

// ⚠️ DANGER: If ALL 5 philosophers get hungry at the same time
//            and each picks up their LEFT chopstick simultaneously...
//            Each holds 1 chopstick and waits for the right one.
//            But everyone's right one is held by their neighbor!
//            CIRCULAR WAIT → DEADLOCK! 💀
What Goes Wrong

Imagine all 5 philosophers get hungry at the same time. P0 grabs C0 (left), P1 grabs C1 (left), P2 grabs C2 (left), P3 grabs C3 (left), P4 grabs C4 (left). Now everyone is waiting for the chopstick on their RIGHT — which is being held by the person to their right. Circular wait. Total deadlock. Nobody eats. They all starve to death. 💀

Three Ways to Fix the Deadlock

1

Allow at most 4 philosophers at the table

If only 4 are sitting, at least one can always eat. No circular wait possible.

2

Pick up BOTH chopsticks atomically (in a critical section)

A philosopher only picks up chopsticks if BOTH are available. Can't hold one while waiting for the other.

3

Asymmetric Solution

Odd-numbered philosophers pick up LEFT first, then RIGHT. Even-numbered pick up RIGHT first, then LEFT. This breaks the circular dependency!

dining_asymmetric.c — FIXED with Asymmetric Solution
// Philosopher i's structure (ASYMMETRIC FIX):
do {
    think();

    if (i % 2 == 1) {
        // ODD philosopher: pick LEFT first, then RIGHT
        wait(chopstick[i]);
        wait(chopstick[(i+1) % 5]);
    } else {
        // EVEN philosopher: pick RIGHT first, then LEFT
        wait(chopstick[(i+1) % 5]);
        wait(chopstick[i]);
    }

    eat();  // 🍜 No deadlock guaranteed!

    signal(chopstick[i]);
    signal(chopstick[(i+1) % 5]);

} while (true);
But Starvation Can Still Happen!

Even after fixing deadlock, starvation is possible. Imagine P0 and P2 are super fast eaters. They can keep grabbing and releasing chopsticks so quickly that P1, P3, and P4 never get a turn — even though there's no deadlock (they could theoretically eat). This is starvation: everyone has a chance, but some never actually eat.

The Big Takeaway

Semaphores are powerful but error-prone. Because wait() and signal() are scattered across processes, one bug can crash everything. That's why higher-level constructs like monitors (next topic) were invented — they hide the semaphore details and prevent common mistakes automatically.
